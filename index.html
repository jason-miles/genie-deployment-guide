Genie deployment guide: from proof of concept to enterprise rollout

Eight steps for taking a Genie Agent from a working demo to a governed, monitored service. Each step gives the action, the gate to pass, and the failure modes seen in practice.

Choose your path

Genie is a family of three experiences on one governed data foundation. Pick the one that matches the job before planning a rollout. This guide follows the Genie Agent lifecycle; Genie One is the way business users reach Agents, and Genie Code is a separate developer track.

0.1 The three products

Genie Agent

0.5 Deployment controls

  • Unity Catalog is the security boundary. An Agent defines the experience; grants, row filters and column masks define what a user can query.
  • One domain per Agent. Narrow Agents answer more accurately than broad ones. Split when scope grows.
  • An owner for every Agent. Agents without an owner lose accuracy as terms and data change.
  • A benchmark gate before production. See Step 04.
  • Channels after quality. Add Teams, Slack or custom apps only once the Agent is production-quality.

01

Discover & scope

Rank candidate topics, name two stakeholders, and write down the questions before any configuration starts. Most stalled rollouts trace back to scope, not technology.

Last verified: 17 Oct 2026 against Databricks documentation. Durations and targets in this step are field-recommended starting points, not published limits.

1.1 What makes a good first topic

  • The data is already registered in Unity Catalog. Delta tables are best but not required. Unregistered data delays the start.
  • A small number of well-documented tables. Start with one to five and prove that related questions are answered correctly before expanding. An Agent accepts up to 50 tables, views or metric views, but accuracy falls as scope grows.
  • Primary and foreign keys are defined and columns have descriptions.
  • The audience is mostly business users. Technical users benefit, but the productivity gain shows most with less technical users.
  • There is a backlog of dashboard and analysis requests for the topic, a large pool of potential users, and the most-used dashboards map to the dataset.
Poor first topicsMetrics where a wrong answer carries severe risk, such as figures in a board report, belong in a reviewed dashboard or a certified query. Open-ended questions that ask for an explanation instead of a data lookup (“why are sales down”) need a different design; test them against the Agent before promising them.

1.2 Rank the candidates

List several topics and rank them. The first topic suggested is rarely the one most likely to succeed. Score each from 1 to 3 and start with the highest total.

CriterionQuestion to ask3 points when
Data readinessIs the data in Unity Catalog and documented?Registered, curated, columns described
Business valueIs there a backlog of requests for this topic?A long backlog and a named decision it speeds up
AudienceHow many business users would ask questions?Dozens or more, across more than one team
StakeholdersAre a business and a technical stakeholder committed?Both named, with time set aside
Error toleranceWhat happens if an answer is wrong?Answers support exploration, not sign-off

1.3 Name two stakeholders

StakeholderRole
Business stakeholderRepresents the end users, preferably someone who is not technical. Defines the questions, the business value and the vocabulary, and promotes the Agent to the user group.
Technical stakeholderOwns the Agent: sets it up, configures it, monitors it, and judges whether the SQL is correct. Typically a BI developer, data analyst or data modeller.

Having both protects the Agent. If one person leaves, the other keeps it alive. Without a business stakeholder, the technical owner tends to chase perfect accuracy while the business users wait.

1.5 Check the data model against the questions

Review the technical stakeholder’s data model before building. Look for a few tables joined by defined primary and foreign keys, ideally a star schema with one fact table at one grain. Avoid duplicate or near-identical column names, mixed currencies, categorical columns with hundreds of distinct values used in filters, and calculations done on the fly. Put calculations in derived columns or views. Run the following to see how much documentation exists:

-- Table-level descriptions for the candidate schema
SELECT table_name, comment
FROM {{cat:main}}.information_schema.tables
WHERE table_schema = '{{sch:sales}}';

-- Columns that still have no description
SELECT table_name, column_name
FROM {{cat:main}}.information_schema.columns
WHERE table_schema = '{{sch:sales}}' AND (comment IS NULL OR comment = '');

02

Data & governance

Make the data trustworthy and the access model explicit before the Agent exists. Genie turns a question into SQL from table and column metadata, so poor metadata produces poor SQL.

Last verified: 17 Oct 2026 against Databricks documentation. Items marked field guidance were not found in public documentation; confirm them with the account team.

2.1 Use curated tables

LayerUse for an Agent?Why
Raw / BronzeAvoidQuality problems, cryptic column names and incomplete records make answers unreliable.
Cleaned / SilverUseValidated, standardised, consistent types.
Aggregated / GoldPreferClearer business logic and pre-calculated metrics.

2.2 Prepare each table in Unity Catalog

Must have

Should have: primary and foreign keys, and governance tags for PII and sensitivity. Good to have: OPTIMIZE unless predictive optimisation is on, and a documented freshness cadence.

COMMENT ON TABLE {{cat:main}}.{{sch:sales}}.{{tbl:orders}}
  IS 'One row per customer order. Refreshed daily.';

ALTER TABLE {{cat:main}}.{{sch:sales}}.{{tbl:orders}}
  ALTER COLUMN order_total COMMENT 'Order value in USD including tax';

-- Keys are informational in Unity Catalog; they tell Genie how tables join
ALTER TABLE {{cat:main}}.{{sch:sales}}.{{tbl:orders}} ALTER COLUMN order_id SET NOT NULL;
ALTER TABLE {{cat:main}}.{{sch:sales}}.{{tbl:orders}} ADD CONSTRAINT orders_pk PRIMARY KEY (order_id);

Put metadata on table and column descriptions first. Only the relevant subset is sent with each prompt, which leaves more context for the question. Avoid repeating column semantics in general instructions.

2.3 Metric Views and the Ontology

A Metric View defines a KPI once in Unity Catalog and applies it wherever the view is queried, so Genie uses the approved definition instead of rebuilding the formula. Prefer Metric Views over Agent-level SQL expressions when a KPI is shared across Agents. An Agent accepts up to 50 tables, views or metric views; start with five or fewer, and use Metric Views or views to pre-join detail instead of adding tables. Genie Ontology adds a semantic layer of business terms, metrics and relationships, governed through metric views, Pages and Domains. It is described in a Databricks blog post and is not yet covered in the Agents documentation, so treat its behaviour as subject to change.

2.6 Grant access with Unity Catalog

GRANT USE CATALOG ON CATALOG {{cat:main}} TO `{{grp:analysts}}`;
GRANT USE SCHEMA ON SCHEMA {{cat:main}}.{{sch:sales}} TO `{{grp:analysts}}`;
GRANT SELECT ON TABLE {{cat:main}}.{{sch:sales}}.{{tbl:orders}} TO `{{grp:analysts}}`;

Row filters and column masks defined in Unity Catalog apply to Genie answers based on the querying user.

CREATE FUNCTION {{cat:main}}.{{sch:sales}}.region_filter(region STRING)
  RETURN is_account_group_member('global_sales') OR region = 'EMEA';
ALTER TABLE {{cat:main}}.{{sch:sales}}.{{tbl:orders}}
  SET ROW FILTER {{cat:main}}.{{sch:sales}}.region_filter ON (region);

CREATE FUNCTION {{cat:main}}.{{sch:sales}}.mask_email(email STRING)
  RETURN CASE WHEN is_account_group_member('pii_readers') THEN email ELSE '***' END;
ALTER TABLE {{cat:main}}.{{sch:sales}}.customers
  ALTER COLUMN email SET MASK {{cat:main}}.{{sch:sales}}.mask_email;
Hiding is not access controlHiding a column in the Knowledge Store changes what Genie considers. It does not stop a user who has SELECT from querying the column elsewhere. Use grants, filters and masks.

03

Build the Agent

An Agent can be created in minutes and is only worth trusting after curation. Build a thin version first, then add structure in layers, using the most structural layer that can express each rule.

Last verified: 17 Oct 2026 against Databricks documentation. The ten-day plan is a field-recommended playbook, not a fixed schedule; a build typically takes one to four weeks from zero.

3.1 The curation hierarchy

Work down this list. Reserve text for behaviour that nothing above it can express. The documentation puts SQL expressions first among Agent-level options, example SQL second and text instructions last.

  1. Unity Catalog metadata. Accurate table and column descriptions, keys and tags. The same work helps every other consumer of the catalog.
  2. Metric Views. Live in Unity Catalog, not in the Agent. They give a deterministic KPI definition that applies wherever the view is referenced.
  3. SQL expressions. Named measures, filters and dimensions in the Agent, reused instead of reinvented per question.
  4. Parameterised example SQL. Verified queries mapped to common question patterns; when a question matches, Genie can use the query directly.
  5. Text instructions. Terminology, formatting and clarification behaviour. They iterate quickly but are open to interpretation.

Each Agent has a limit of 100 instructions, where every example SQL query, every SQL function and the whole general-instructions block counts as one.

3.2 What the Knowledge Store holds

Table and column descriptions, synonyms, join relationships, SQL expressions, prompt matching settings and column values. Everything in it is scoped to the Agent and does not change Unity Catalog. Turn on entity matching for categorical columns (regions, statuses, product names) so a prompt that says “Florida” resolves to a stored value of “FL”, and enable format assistance on important columns so Genie sees representative values. Define join relationships so joins are consistent, or pre-join frequently joined tables into views.

3.3 Sample questions

Configure 6 to 10 sample questions per Agent. Write literal questions with the real metrics and entities the Agent owns, not templated placeholders, and mirror the patterns your trusted assets cover:

  • What was revenue for Q1 2026?
  • Who are the top 10 customers by bookings this year?
  • How does gross margin compare across regions?

3.4 Example configuration

-- SQL expression (measure): net revenue
SUM(order_total) - SUM(returns_total)

-- Parameterised example SQL, with the phrasing it answers in a comment
-- "What was revenue for EMEA in Q1?"  "Show Q1 EMEA sales"
SELECT SUM(order_total) AS revenue
FROM {{cat:main}}.{{sch:sales}}.{{tbl:orders}}
WHERE region = :region AND order_quarter = :quarter;

3.6 Troubleshooting

SymptomFix
Misunderstands jargonPrecise column descriptions and Agent-scoped synonyms; example SQL that shows the interpretation; short text for critical terms
Uses the wrong tablesRemove extra tables; pre-join into governed views or metric views; say in table descriptions which table is authoritative
Uses the wrong columnsHide internal columns; clearer names and descriptions; entity matching on representative columns
Filters on values that do not existSample values for key dimensions; define canonical filters as SQL expressions
Joins incorrectlyMove joins upstream into views with explicit keys; document joins in the Knowledge Store and example SQL where keys cannot be set
Computes metrics differently from dashboardsDefine the metric as one SQL expression; remove conflicting guidance; promote critical metrics to trusted assets
Ignores instructionsShorten and prioritise; move logic into expressions or example SQL; put global behaviour at the end of the instructions
Slow or timing outUse a pro or serverless warehouse with CAN USE; keep datasets small; pre-aggregate in metric views. Genie cancels queries over 5 minutes and messages over 30 minutes
References tables or columns that do not existConfirm assets are registered in Unity Catalog and still match; Agent edits do not overwrite Unity Catalog metadata
High-stakes answersFor financial reporting, compliance or safety questions, encode the logic as SQL expressions and trusted assets (parameterised queries or SQL functions) instead of free-form generation, and keep a gold-question benchmark suite that validates every change.
04

Benchmark & validate

A production Agent is one that has measured accuracy. Benchmark first, let technical users live with the Agent, then bring in business power users.

Last verified: 17 Oct 2026 against Databricks documentation. Durations and the accuracy target are field guidance and are not published limits.

4.1 Build the benchmark suite

A benchmark is a question paired with the SQL that answers it correctly. Cover the 15 to 20 questions users are most likely to ask, with two to four phrasings each: roughly 30 to 80 benchmarks. An Agent supports up to 500. Use the auto-suggested benchmarks to seed the set. Cover these categories:

  • Simple aggregations: “What is total revenue?”
  • Time-based queries: “How did sales compare month over month?”
  • Filtered queries: “Show me only enterprise customers.”
  • Multi-table joins: “Which products did our top customers buy?”
  • Top-N rankings: “Who are our top 10 accounts by revenue?”
  • Complex business logic: “What is our customer churn rate?”

Benchmarks run as independent conversations without threaded context. In chat mode a result counts as good when the SQL matches exactly or the result set matches, allowing for different sorting and rounding to the same four significant digits.

4.2 Run and read results

Run the suite after every significant change to instructions or data, and track the score over time. The benchmark evaluation commands are in Beta and may change.

# Start a benchmark run, then read it back (Beta commands)
databricks genie genie-create-eval-run {{spc:01ef0000000000000000000000000000}} --profile <profile>
databricks genie genie-get-eval-run {{spc:01ef0000000000000000000000000000}} <eval-run-id> --profile <profile>
databricks genie genie-list-eval-results {{spc:01ef0000000000000000000000000000}} <eval-run-id> --profile <profile>
The 80% gateField guidance is to hold an Agent at about 80% benchmark accuracy before promoting it. This number is not in the public documentation, so treat it as a starting point and set the threshold per use case. Below the gate, an Agent is not ready regardless of how it feels in a demo.

Onboard about five business power users, preferably those who defined the scope. Temporary workspace access with SQL entitlements and permission to run the Agent is enough; the full access setup comes in Step 05. Run this for 1 to 2 weeks (field-recommended). Major changes restart the timer.
